1. Challenge Deconstruction
What Is ENAM Looking For?
ENAM Holdings is Nemish Shah's firm - legendary value investors who do deep, primary-source, fundamental research. They are not momentum traders; they are patient, rigorous bottom-up investors. This context matters enormously for what "good" looks like:

They want to see primary data discipline - not noise from news or broker notes
They value judgment over completeness - what earns attention, what doesn't
They want a product viewpoint, not a data dump
Efficiency matters to them (they're value investors after all) - smart spending on compute earns bonus points
The Core Tension: Push vs. Pull
The challenge cleverly forces you to solve two fundamentally different problems:

Dimension	Push Mode	Pull Mode
Trigger	Time / event-driven	User query
Data	EOD prices + exchange filings	Annual reports + concall transcripts
LLM task	Classify, summarize, enrich, alert	RAG, analyze, compare, synthesize
Latency	Can be async (nightly batch)	Must feel fast (<5s)
Volume	High (many events)	Low (per stock)
Cost	Must be cheap	Can spend more per query
Key Constraints (Hard)
Mobile-first - everything must work beautifully on a phone
No broker notes / news for pull analysis - only annual reports and concall transcripts
Must generalize - the engine must work on any NSE ticker, not just demo stocks
Must run - a broken demo is the worst outcome
Primary sources only for pull - no external LLM knowledge of company
Grading Priorities (from the brief)
Creativity + product sense + judgment (highest weight)
Architecture quality
Thin-but-working > broad-but-broken
Compute efficiency (bonus)

RAG architecture:

PDF → pdfplumber → semantic sections → chunk (2000 tok parent / 400 tok child)

3. AI/LLM Pipeline Design
Smart Model Routing (Cost Efficiency = Bonus Points)
Task	Model	Rationale
Announcement classification (bulk)	Gemini 1.5 Flash / GPT-4o-mini	Cheap, fast, 1M+ token context
Announcement summarization (1-liner)	Gemini 1.5 Flash	Same
Quarterly results extraction (Revenue, EBITDA, PBT, PAT)	GPT-4o-mini with structured output	JSON mode, reliable on tables

Bull vs. Bear case	Claude Opus / GPT-4o	Critical thinking required
Caching strategy:

Cache annual report embeddings in ChromaDB persistently
Cache announcement summaries in SQLite
Cache company bio enrichments (change infrequently)
Re-fetch price data daily only
Push Engine Design
1. Windowed Digest
Trigger: User opens app / scheduled notification
Input: All filings for portfolio companies in the last 24h (or custom window)
Process:
  1. Pull announcements from NSE/BSE for each portfolio stock
  2. Classify each → priority label
  3. Filter: Remove "unclassified" from main view
  4. Summarize each in 1-2 lines (cheap LLM)
  5. Enrich HIGH priority items deeper
  6. Sort: HIGH → MEDIUM → LOW → (collapsed SKIP)
Output: Ranked feed of cards

Flag overperformance/underdelivery patterns
Summarize management's track record of honest guidance

6. Critical Design Decisions
Decision 1: What to build first (MVP)
Given "thin-but-working beats broad-but-broken":

MVP Priority:

Push digest (windowed) for 15-20 portfolio stocks
Quarterly results extraction (Revenue, EBITDA, PBT, PAT QoQ/YoY)
Management change enrichment (bio)
Pull: Business snapshot + Narrative vs. Numbers
Alert configuration UI
Nice-to-have (if time):

Full 8-module pull analysis
Voice interaction
Push notifications
Decision 2: How to handle NSE scraping reliability
NSE blocks scrapers aggressively. Strategy:

Use nsetools and jugaad-trader Python libraries as primary
Manual session cookie approach as backup
Pre-populate the announcement cache at launch (not real-time)
Store announcements in SQLite, refresh daily
Decision 3: RAG vs. LLM-with-full-context
For pull analysis, we have two approaches:

RAG: Embed chunks, retrieve relevant sections → cheaper but may miss context
Long-context LLM: Feed entire annual report PDF to Claude 3.5 (200k context) → more expensive but better synthesis
Hybrid approach:

Use RAG for specific numerical queries (faster, cheaper)
Use long-context LLM for synthesis tasks (Narrative vs. Numbers, Bull/Bear)
Cache all results aggressively
Decision 4: Announcement classification - prompt vs. fine-tuned model
Given we have 17 clearly defined categories with examples, a well-crafted prompt to Gemini Flash reliably classifies announcements. No fine-tuning needed. Accuracy should be ~95% on these clear categories.

10. Risks and Mitigations
Risk	Mitigation
NSE scraper gets blocked	Pre-cache announcements offline; use RSS fallback
Screener.in layout changes	Store downloaded PDFs locally; don't re-fetch live
LLM hallucination on numbers	Always cite source chunk; verify against structured yfinance data
ChromaDB slow on large corpus	Index only last 3 years of filings; precompute embeddings
Frontend looks basic	Use shadcn/ui + Framer Motion; invest heavily in design
Demo crashes	Pre-populate entire demo flow with cached data
PDF parsing fails	Fallback: use pdfminer, then PyMuPDF, then OCR (Tesseract)
11. Key Insight: Why This Challenge Is Really About Judgment
The brief says: "the judgment is the point." This appears 3+ times.

Every design choice is a judgment:

Which announcement categories get expanded cards vs. collapsed?
What threshold defines "unusual" price movement?
Which financial ratios appear in the snapshot?
How long is a "short summary" for a management change?
What does "strong deal wins" look like in numbers?
The winners won't be the ones who built the most features. They'll be the ones whose judgment about what an investor cares about is demonstrably right. The writeup must articulate this judgment explicitly.
